# Tools

Every script/binary this project provides, in one place, each linking to
the lifecycle doc that explains it in full context. For what these tools
touch (env vars, volumes, ports), see [Reference](4.1-configuration.md).

| Tool | Purpose | Explained in |
|---|---|---|
| `scripts/setup-dev-environment.sh` | Bootstrap a fresh dev machine (Rust toolchain, wasm target, `dioxus-cli`/`wasm-bindgen-cli`, `sccache`, Docker) | [Setup](3.1-setup.md#development-environment-setup) |
| `scripts/services.sh` | Start/stop/restart/status/logs for the local backend + web dev server | [Development](3.2-development.md#quick-start-scripts) |
| `scripts/desktop.sh` | Launch a desktop client against the local backend | [Development](3.2-development.md#quick-start-scripts) |
| `scripts/admin.sh` | Operator CLI (`tile-lite-elite-admin`) wrapper for a **local** dev server — list/delete users, reset passwords, list/delete/force-end games | [Production Environment & Operations](3.4-production-environment.md#admin-cli) |
| `tile-lite-elite-admin` (binary) | The same operator CLI, run directly — locally via `admin.sh`/`cargo run -p admin-cli`, or against a container via `docker compose exec` | [Production Environment & Operations](3.4-production-environment.md#admin-cli) |
| `scripts/deploy-preview.sh` | Build and run the preview stack locally: `up`/`down`/`reset`/`at <ref>`/`at prod`/`verify` | [Testing, CI & Release](3.3-testing-ci-and-release.md#26-preview-environment) |
| `docs/diagrams/` | Mermaid sources for the pre-rendered diagrams, and how to re-render them | [`docs/diagrams/README.md`](diagrams/README.md) |
| `scripts/ci-status.sh` | Did a **named** CI run pass for a commit? `--run <event>[:<branch>]` picks it and is required; `--require <job>` insists a job ran and passed; `--wait` blocks until it finishes; `deploy.sh` uses it as the release gate | [Gating on a particular run](3.3-testing-ci-and-release.md#2131-gating-on-a-particular-run) |
| `scripts/status.sh` | Where every open change is, what each environment is running and how far behind `main`, what a release from `main` would ship, and which documents are overdue a read | [Releases are branches](3.3-testing-ci-and-release.md#28-releases-are-branches) |
| `scripts/check-release-version.sh` | Refuse a patch release that carries functional change — reads the milestone's labels; `deploy.sh` runs it as a release gate | [Releases are branches](3.3-testing-ci-and-release.md#28-releases-are-branches) |
| `scripts/check-commit-stamp.sh` | Check commit subjects carry `app <X.Y.Z> api <M.N>:` and that the numbers match the tree; CI runs it per push | [Version numbers: which to bump, and when](3.3-testing-ci-and-release.md#27-version-numbers-which-to-bump-and-when) |
| `scripts/deploy.sh` | `DEPLOY_GATES_ONLY=1` to ask whether a deploy would be allowed, without building anything. Otherwise: build images locally from a fresh checkout of a commit (`HEAD`, or any ref — that's also how you roll back) and ship them to the production VM | [How `deploy.sh` ships an image](3.3-testing-ci-and-release.md#213-how-deploysh-ships-an-image) · [Rolling back](3.3-testing-ci-and-release.md#211-rolling-back) |
| `scripts/rollback.sh` | Put production back to the previous images *and* the database snapshot taken with them — `deploy.sh` calls it automatically when a deploy fails, and it is the **first thing to reach for** when production is broken | [Rolling back across a migration](3.3-testing-ci-and-release.md#2111-rolling-back-across-a-migration) |
| `e2e/` (`npm test`) | Playwright end-to-end UI tests — drive the real web client in a browser against a running dev environment | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) · [`e2e/README.md`](../e2e/README.md) |
| `scripts/actions.py` | What is waiting on you, in workstream order — parent issue, its sub-issues, their pull requests, and the unchecked items under each issue's `Open actions` heading. `--claude` for the other side, `--all` for everything | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `scripts/inbox.sh` | What has been said on GitHub since you last looked — comments grouped by issue, marked with who typed them. Takes a window in days | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `scripts/roadmap.sh` | What is in each release, in release order, and what waits on what | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `scripts/check-docs.sh` | The documents' own gate: markdownlint, every internal anchor link resolves across `docs/`, and change documents are in an issue or release folder. **CI runs it on every push**, so the check made by hand and the one enforced are the same code | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `scripts/check-doc-links.py` | The link half of the above, on its own — 81 anchor links broke silently when `docs/3.3` was renumbered, and a bad anchor never errors: it lands the reader at the top of the page | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `scripts/e2e-clean.sh` | Purge `e2e-*` test players and their games from the dev DB (Playwright teardown; also runnable by hand) | [`e2e/README.md`](../e2e/README.md) |
| `scripts/check-rate-limits.sh` | Does the running server refuse a caller who asks too often, and keep answering everybody else? Run against rehearsal as the release gate for a change with nothing to look at | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `cargo run --release --example rate_limit_load` | Load test: takes the limits to where they trip, on rehearsal hardware, and asserts the rules rather than the throughput. Appends to `rate_limit_results.csv`. Refuses to run against production | [Testing, CI & Release](3.3-testing-ci-and-release.md#1-what-to-type) |
| `cargo run --release --example engine_timing_bench` | How long an engine move takes, across real games. Appends to `engine_timing_results.csv` | [Testing, CI & Release](3.3-testing-ci-and-release.md) |

Underlying infrastructure these scripts drive, rather than tools you invoke directly: `docker compose` (`docker-compose.yml` for production, `docker-compose.preview.yml` for preview), the shared `Dockerfile` both build from, Caddy (`Caddyfile`/`Caddyfile.preview`) for reverse-proxying and TLS, and SQLite for persistence — see [Container Topology](3.4-production-environment.md#container-topology) for the request-flow picture and [4.1 Configuration](4.1-configuration.md#infrastructure-configuration) for exactly how each is configured (journal mode, pool size, Caddy's routing/caching rules, Docker's stage/image layout).
