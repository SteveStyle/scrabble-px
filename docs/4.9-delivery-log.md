# 4.9 Delivery log

One row per delivery, for somebody asking **what changed in production, and
when.** Not a runbook — a runbook holds every step for somebody doing it or
undoing it, and lives with its project. This holds the fact that it happened.

**It starts at #174.** Deliveries before 2026-08-22 are recoverable from the
`prod-*` tags and the closed milestones, and are not retrofitted here: a log
back-filled from memory would claim a completeness it does not have. The tags
are the record for everything earlier.

**Identifiers.** A delivery that ships application code is a release and takes
its version. A delivery that ships none — a host change, a console change, a
drill — takes the production version at the time plus a letter: `0.7.0a`, then
`0.7.0b` (D34). The letter form is not valid semver, deliberately: `deploy.sh`
reads its milestone from `Cargo.toml`, so a lettered milestone can never be
matched by a deploy and can never auto-close. These rows are closed by hand.

## What each delivery left behind that git does not show

`0.7.0a` is the first row where most of the change exists only on the host and
in the OCI console. `docs/4.8-artefacts.md` is the register of those; this log
records only that the delivery happened.

**Two defects were found by running it**, both fixed the same evening:

- `sqlite3` was in the server image but not on the host, and the backup's
  integrity check runs on the host. The first real run failed.
- All three marker uploads used `curl -T -`, which sends chunked encoding; OCI
  answers **501**. Since every alarm watches a marker for absence of success,
  not one could ever have been satisfied — #199.

Neither was visible from the repository. Both were found by the delivery's own
step 3, which is the argument for proving a delivery rather than declaring it.
