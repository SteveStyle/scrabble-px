# Persistence

## SQLite File Layout

The project should use one primary SQLite database file per environment.

Typical examples:

- local development: `./data/tile-lite-elite.sqlite3`
- self-hosted instance: `/var/lib/tile-lite-elite/tile-lite-elite.sqlite3`
- tests: temporary throwaway database files

SQLite may also create sidecar files when write-ahead logging is enabled:

- `tile-lite-elite.sqlite3-wal`
- `tile-lite-elite.sqlite3-shm`

Those files are part of normal SQLite operation and do not represent separate databases.

## What Is Persisted

The database should store durable game and platform data such as:

- active games and finished games
- board state snapshots or move history
- tile bag state and player racks if needed for recovery
- player or session records
- engine metadata and configuration
- match results and audit history
- saved game metadata
- migration version state

## What Stays In Memory

The following should generally stay in memory or be recomputed:

- current UI state
- transient preview calculations
- temporary engine search state
- cached move evaluations that can be rebuilt

## Persistence Model

The server remains authoritative and writes the canonical state to SQLite.

Clients and engine proxies may use the shared rules library for previews, but they do not own persistence.

Good persistence behavior for this project means:

- a match can be resumed after a restart
- finished games remain available for history and replay
- the database can be backed up by copying the single main file, ideally after a clean shutdown or with WAL-aware backup procedures
- the design stays simple enough to run locally or on a free tier

## Recommended Approach

Use migrations to evolve the schema over time.

Prefer simple, explicit tables over complex embedded blobs unless a blob is the clearest way to capture a replay snapshot.

Keep the write path small and predictable so the project stays easy to self-host.

## Retention: how long a game is kept

Design note for #42. **Not yet implemented** — this records the shape agreed
before code, per docs/3.3's rule for a `major-function` change.

### The problem

Games are never deleted. Every game ever played stays in the database and,
per issue #29, in memory — `AppState::new` loads all of them at boot. So resident
memory and startup time are proportional to *cumulative* games, not active
ones, and both grow forever.

Measured 2026-08-03: 37 games in production, ~46 KB each. Disk is not the
constraint — that is on the order of a million games before it matters.
Memory is, on a 954 MB box.

### What is deleted, and when

| status | clock | why |
| --- | --- | --- |
| `Waiting` | since `updated_at` | a game nobody ever joined; the Godot case |
| `Finished` / `Aborted` | since it ended | the bulk of them, eventually |
| `Active` | since `updated_at` | **backstop only** — see below |

An active game normally resolves itself: `apply_move_timeout` retires a seat
that overruns `move_time_limit_seconds`, and the game finishes once at most
one active seat remains. Every game has a limit — it defaults to 72 hours and
is bounded to 1 hour..40 days (#43) — so "eventually" is at most a few weeks.
The `Active` retention period is therefore a backstop against a bad value or
a stuck state, not the normal path.

### Where the sweep runs

Alongside `sweeps::expire_overdue_turns`, which already iterates **every**
loaded game rather than only the one a handler touched, and is called at the
top of any handler that reads live games.

That gives a useful property: **growth requires use, and use triggers the
sweep.** A server nobody plays accumulates nothing; one being played cleans
itself on every request. No background scheduler — which this server
deliberately does not have.

### What survives

`player_ratings` and `rating_history` are separate tables, so a player's
rating and its history outlive the games they came from. That is what makes
deleting games acceptable at all.

**To confirm when implementing**: that no statistic is computed by counting
game rows. If one is, retention would silently change players' numbers.

### Open questions

- **Warning before deletion.** A finished game vanishing is probably fine; a
  waiting game someone meant to start is more annoying. There is no "keep
  this" concept — `removed_by_player` only hides a game from one player's own
  list.
- **No export.** Deletion is irreversible and there is no archive. Worth
  deciding whether an admin command should be able to export before the sweep
  reaches something.
- **Periods themselves** are not fixed here. They want to be configurable,
  with defaults chosen once there is a real sense of how long a game sits
  finished before nobody looks at it again.

### Why this rather than #29's proposal

Issue #29 suggested lazy loading or eviction so memory stops tracking all-time
games. Retention is better: it bounds the *set*, so memory, startup time and
disk all follow from one change. #29 becomes worth doing only if the retained
set is itself too large — at ~46 KB per game, not for years.
