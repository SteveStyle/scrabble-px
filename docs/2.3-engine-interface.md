# Engine Interface

## Purpose

The engine interface allows different computer opponents to plug into the server and participate in games.

The engine logic should remain separate from the shared rules logic. Engines may consume shared rules data and helper functions, but they should not own the canonical rules model.

This supports:

- human vs engine play
- engine vs engine play
- benchmarking engines against each other
- swapping strategies without changing the game server

## Requirements

An engine implementation should be:

- deterministic for a given input state when possible
- versioned
- observable through logs and metadata
- safe to run through a server proxy

## Core Contract

At minimum, an engine needs to accept a game snapshot and return an action.

Conceptually:

- input: current game state, player seat, legal move constraints, time budget, supported language word list
- output: chosen move, pass, exchange, or resign

## Suggested Interface Shape

An engine should expose:

- metadata: name, version, author, supported variants
- capability flags: supports timed play, supports analysis, supports ranking
- move generation: produce the next action from a game state
- optional diagnostics: explanation, candidate moves, search depth, timing

Engine implementations may also keep private state for search trees, opening books, evaluation caches, and tuning values that are not part of the shared rules layer.

## Server Proxy Responsibilities

The server proxy should:

- translate game state into the engine request format
- use the shared rules library to preview legality and score candidates
- enforce time limits
- validate the engine response
- reject illegal actions
- record the engine move in the authoritative game history
- isolate the engine from direct access to clients

This keeps the proxy responsive for engine authors while ensuring the server remains the final authority.

## Engine Interface Versioning

The engine interface must be versioned from the start.

That prevents old engines from breaking when the game state or rule model changes.

## Testing Strategy

Every engine should be testable through the same harness.

Useful tests:

- engine can produce a legal move from a standard opening state
- engine respects time budget
- engine-vs-engine match completes without server errors
- engine response is rejected when it becomes illegal

## Reading an engine timing run

`cargo run --release --example engine_timing_bench [games] [edition]` plays
engine-vs-engine games through the same `maybe_run_engine_turn` the server uses,
and appends a row to `engine_timing_results.csv`.

**Compare CPU against wall before anything else.** Each move is timed twice: wall
clock, and CPU time from `CLOCK_PROCESS_CPUTIME_ID`. If `cpu_p99_ms` is far below
`p99_ms` the move was waiting. The converse does **not** hold on a virtual
machine, and assuming it did produced a wrong conclusion on 2026-09-03.

**On the deployment VMs, `cpu_ms` cannot be trusted in the tail.** A guest kernel
attributes time to a process that the hypervisor did not actually give it, so a
stolen move can report CPU time equal to its wall time and read as hard work.
What settles it is comparing the *same move* on two machines, which the
benchmark makes possible because the games are seeded and deterministic:

| | |
| --- | --- |
| ordinary moves, VM against laptop | **1.8x** — the honest machine difference |
| tail moves that report `cpu ≈ wall` | **26x** median, 319x at worst, for identical work |

A 26x spread on the same deterministic move, between machines that differ by
1.8x everywhere else, is not a property of the search. The tail also clusters:
16 of 27 slow moves land in a single 50–59 ms bucket, where genuine work spreads
smoothly. Both are the hypervisor descheduling the vCPU.

**Which statistic to read, and it is not the p99.** The outliers are few — 27
of 1229 — so everything above about p97.8 is inside them and everything below is
not. Between the same two machines on 4 September:

| | median | p95 | p99 |
| --- | --- | --- | --- |
| VM against laptop | **1.6x** | **2.4x** | 12.9x |

Median and p95 track the hardware. The p99 tracks who else is on the host. So
compare median and p95 between runs, and treat a p99 from a VM as saying nothing
about this code.

**The run says so itself.** `slow_moves` counts moves over 20 ms and
`slow_cpu_starved` the subset that used almost no CPU while they waited. The
threshold is not tuned: on a machine nobody else is sharing nothing reaches it —
the slowest of 1229 laptop moves was 16 ms — while descheduling gaps cluster at
50-60 ms. A non-zero count prints a warning naming which statistics survive it.
`slow_cpu_starved` is the provable subset only; the rest cannot be told from
work by the process itself, which is why both numbers are kept.

**So the algorithmic tail is only readable on a machine you own.** On the laptop,
every move over 20 ms has a blank in the rack, and moves with a blank run at
6.3x the median — one blank multiplies the search by the letters it could stand
for. That is the real shape of the distribution, and it is invisible under the
VM's scheduling noise.

**Steal is machine-wide and per-run**, not per-move: the kernel does not record
who lost the time. `steal_pct_of_capacity` is against wall time times cores, so
it is the share of the whole machine the hypervisor took, and 100% would mean
every core all run.

**The host is the hostname**, never typed. What the machine is comes from the
`cpu_model` and `cores` columns. An earlier `BENCH_HOST` override produced three
labels for two machines, which read as three until somebody checked.

**Running on a deployment VM**: neither VM has a Rust toolchain and both run the
same glibc as the development machine, so build here and copy the binary rather
than installing one there.

```bash
cargo build --release --example engine_timing_bench -p server-game
scp target/release/examples/engine_timing_bench tile-lite-elite:/tmp/
ssh tile-lite-elite '/tmp/engine_timing_bench 30 official'
ssh tile-lite-elite 'rm -f /tmp/engine_timing_bench'
```

It peaks at 24 MB resident and uses one of the two cores for a few seconds. The
run prints its CSV row to stdout, because on the VM there is no
`CARGO_MANIFEST_DIR` to append to and no `git` to say what was built: paste the
row into the CSV here and replace its `unknown` commit with the one the binary
was built from.
