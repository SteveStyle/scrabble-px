## User testing complete — nothing for the owner to do

### #27 — Login timing reveals whether a display name exists

`080ef2e`. An unknown display name now verifies the supplied password against
a real Argon2 hash (`DECOY_PASSWORD_HASH`) rather than returning early, so a
known and an unknown name cost the same work.

Not user-testable by observation: the whole point is that the two cases look
identical. Timing is what would show a regression, and that is a measurement
rather than a judgement.

### #99 — The hashing pool's 503 sends a fixed `Retry-After`

`68f23dc`. The hint is jittered, so a crowd refused together does not return
together.

Verified by sampling live `Retry-After` values during the 0.5.1 release.
Nothing a person can see in normal use.

### #33 — Offensive language: a narrow ban for everyone, a wider restraint for bots

Nine commits. The greylist ships with **2,573 words** Greedy Bot will not
play; the denylist ships empty, which is deliberate — what a bot will never
play is the *union*, so the greylist alone is the whole protection, and the
denylist only decides what a **person** may play.

**You are right that you cannot really test this.** Greedy has to be handed a
position where a greylisted word is the highest-scoring move, which will not
happen by chance. That case is now covered automatically:
`the_bot_declines_a_greylisted_word_that_would_have_won` — an empty board and
a rack of Z/E/X, which the dictionary allows exactly two words from: `ZEX` at
38, greylisted, and `EX` at 18, clean. It asserts the bot takes `EX`, and
carries a control asserting the unrestrained engine really would have taken
`ZEX`.

**Greedy should not seem different**, and that is the expected result. It has
lost 0.96% of its vocabulary, and the timing is unchanged: 0.23 ms median
against 0.25 ms with an empty list. If it *does* seem different, that is worth
reporting — it would mean something other than the greylist changed.

Remaining, and not blocking: **#116**, curating the denylist.

### #115 — A repeatable pipeline from published word list to trie

Covered by the fixed-point invariant (each committed list is exactly what
`normalise` produces), the denied-word test, and provenance verification: all
four upstreams now carry a SHA-256, and three reproduce the committed file
byte-for-byte.

## Ready for the owner

### #90 — Record what the database holds, daily

`3f4515a`. A row per day in `database_size_history`, written by a lazy sweep
off `list_games`, with `recorded_on` as the primary key so "once a day" is
enforced by the schema.

**How to see it.** The admin CLI reads it. Preview's server is in a container
and `/admin/*` only accepts loopback, so it has to run *inside* the container —
`scripts/admin.sh` targets the host's `127.0.0.1` and will not reach it:

```bash
docker compose -f docker-compose.preview.yml exec server tile-lite-elite-admin size
```

Preview already has two days:

```text
DAY         PLAYERS  SESSIONS  GAMES  INVITES  CHAT  IN MEMORY  DB BYTES
2026-08-13  16       3         13     11       28    13         544768
2026-08-12  16       10        16     16       24    16         544768
```

`--json` gives the unabridged records.

**What to check:** that the numbers match what you believe is there, and that
today's row updates as you test. **A missing day means the server saw no
requests that day, not that it broke** — the sweep is lazy.

### #82 — Do not delete an account that is currently signed in

`1be1f3b`. `users delete` is refused for a player with a live session.

**How to reach the admin CLI in Preview** — same as #90, inside the container:

```bash
docker compose -f docker-compose.preview.yml exec server tile-lite-elite-admin users list
docker compose -f docker-compose.preview.yml exec server tile-lite-elite-admin users delete <player_id>
```

**Suggested test:** sign in as a throwaway account in a browser tab, leave the
tab open, try to delete it — expect a refusal naming the reason. Then sign out
in that tab and delete it again — expect it to work.

`users delete` has no confirmation and no undo, so use an account you do not
mind losing.

### #50 — The client keeps stale game state when its session ends

Four commits, and the bug is in *"the session ended"* rather than in *"the
account was deleted"* — which is why there are four paths worth trying rather
than one:

1. **Log out** with a game open. The board should clear, not sit behind the
   auth dialog.
2. **Account deleted while signed in** (via #82's CLI, from a *different*
   account than the one you are testing #82 with). The original symptom:
   Register dialog prefilled over a still-visible board, and registering as a
   new user left the previous user's tiles on screen.
3. **Session expiry** — harder to force by hand; deleting the session server-side
   is the practical route.
4. **A 403 that is not a 401.** `ec72268` changed four handlers from 401 to 403
   for "signed in but not allowed". Worth confirming that being refused
   something does *not* log you out — that regression was introduced and fixed
   during this release, so it is the one most worth re-checking.

The thing to watch in all four: no fragment of the previous position remains
visible, in the board, the rack or the games list.

### #76 — Name autocomplete dropdown does not appear when inviting

Five commits. The one that mattered was `23ac5f0`: the dropdown was being
**clipped**, not missing — which is why three probes reported it working.
`toBeVisible()` and node counts both pass against a clipped element; only
hit-testing with `document.elementFromPoint` caught it, and that is now in the
e2e suite.

Also in this issue: Enter adds a seat, blur puts suggestions away, a name
matching nobody is refused rather than silently accepted, and a named seat
takes the invitee's registered spelling.

**Worth retesting in Preview** because it was fixed against Dev, and the
clipping was a layout effect — different container, worth confirming.

### #12 — Mobile: reclaim vertical space above the rack

`9799140`, one CSS change: `.preview-slot` from **80px to 60px**. The tallest
thing it holds is a legal-move banner at a little over 50px, so every other
state was carrying ~20px of dead air directly above the rack.

Still a fixed height rather than `min-height`, deliberately: the slot sits
immediately above the rack, so one that grew when a preview appeared would
shift the tiles out from under your thumb mid-move.

**The other half of the issue was deliberately not done**, and it is the
bigger half. `Shuffle` occupies a row of its own above Pass/Exchange/Play,
worth about 50px — more than twice the slot trim. It is stacked by an explicit
mobile rule whose comment records what it solved: with the groups sharing a
row on a narrow screen they each wrapped independently and the result
scrambled, stranding Pass alone above Shuffle/Exchange/Resign with Play on a
third line.

**So the question for your phone is a judgement, not a check:** is ~20px
noticeable, and is the Shuffle row worth re-opening that trade? Merging the
rows back is not a CSS tweak — it is re-deciding something that was decided
once against a real phone, which is why it wants your eye rather than a guess
against a stylesheet.

### #86 — The unread-message indicator: where it appears, and when it clears

`709489d`. The watermark was changed to mean **seen** rather than **arrived**:
messages must be visibly on screen for 10 seconds before the mark clears, and
a new message restarts the count.

You have been testing this with two sessions passing messages. **Being
recreated in Playwright** — two browser contexts, two accounts, messages both
ways with varying gaps — so the timing cases can be exercised repeatedly and
reported rather than remembered.

What automation can settle: whether the mark appears on arrival, survives the
panel being scrolled off screen, survives the tab being backgrounded, clears
after 10 seconds of genuine visibility, and restarts on a new message.

What it cannot: whether the fade *reads* right. That is your judgement and it
has already produced one design change — the fade being the signal rather than
the colour.

**Send your notes when convenient.** Even rough ones are worth more than my
guesses about which tweaks you have in mind.

## Deferred to Rehearsal

### #67 — An idle tab never picks up a new client bundle

Six commits. The client now polls `/version.txt` and compares the **build id**,
having dropped the bundle hash as a fourth version.

**Agreed: this is one for Rehearsal.** It cannot be tested in Preview in any
meaningful way, because the failure needs a *deploy to happen underneath a tab
that has been sitting idle across it* — which is a property of the deployment,
not of the build. Rehearsal is the first environment where that is a real
event.

**The test at Rehearsal:** leave a tab on the landing page, deploy over it,
then use the tab without refreshing. It should pick up the new build. The
original symptom was a tab still reporting the old build id after starting a
game and playing a move, with only a manual refresh moving it.

## Notes
