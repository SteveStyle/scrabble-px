## Ready for user testing

### #76 — Name autocomplete dropdown does not appear when inviting

Five commits. The one that mattered was `23ac5f0`: the dropdown was being
**clipped**, not missing — which is why three probes reported it working.
`toBeVisible()` and node counts both pass against a clipped element; only
hit-testing with `document.elementFromPoint` caught it, and that is now in the
e2e suite.

Also in this issue: Enter adds a seat, blur puts suggestions away, a name
matching nobody is refused rather than silently accepted, and a named seat
takes the invitee's registered spelling.

**Worth retesting in Preview** because it was fixed against Dev, and the
clipping was a layout effect — different container, worth confirming.

### #12 — Mobile: reclaim vertical space above the rack

`9799140`, one CSS change: `.preview-slot` from **80px to 60px**. The tallest
thing it holds is a legal-move banner at a little over 50px, so every other
state was carrying ~20px of dead air directly above the rack.

Still a fixed height rather than `min-height`, deliberately: the slot sits
immediately above the rack, so one that grew when a preview appeared would
shift the tiles out from under your thumb mid-move.

**The other half of the issue was deliberately not done**, and it is the
bigger half. `Shuffle` occupies a row of its own above Pass/Exchange/Play,
worth about 50px — more than twice the slot trim. It is stacked by an explicit
mobile rule whose comment records what it solved: with the groups sharing a
row on a narrow screen they each wrapped independently and the result
scrambled, stranding Pass alone above Shuffle/Exchange/Resign with Play on a
third line.

**So the question for your phone is a judgement, not a check:** is ~20px
noticeable, and is the Shuffle row worth re-opening that trade? Merging the
rows back is not a CSS tweak — it is re-deciding something that was decided
once against a real phone, which is why it wants your eye rather than a guess
against a stylesheet.

## Reaching the data

| | admin CLI | SQLite |
| --- | --- | --- |
| dev | `sadev` | `dbdev` |
| preview | `sapre` | `dbpre` |
| production | `sa`, on the VM | `dbprod` |

All six are in `~/.bashrc`, written by `scripts/setup-dev-environment.sh`. The
`db*` three are `-readonly`, so none of them can write — which matters most for
`dbprod`, sitting one keystroke from `dbpre`.

The aliases exist because *where* the CLI runs is the access control: `/admin/*`
accepts loopback only, and the host's `127.0.0.1` is not a container's.

```bash
dbpre                                             # interactive
dbpre "select recorded_on, players from database_size_history;"
```

Do not reach for the volume's host path — it is root-owned and needs `sudo`.
If you copy the database out to read it with your own `sqlite3` instead, take
the `-wal` and `-shm` files too: Preview's WAL currently holds 1.3MB the
`.sqlite3` file does not, so copying one file reads as a stale database rather
than as an error. Full detail in
[3.4](../3.4-production-environment.md#inspecting-the-database).

## Notes

- Preview's data volume persists across redeploys, so games and accounts
  accumulate. `./scripts/deploy-preview.sh reset` wipes it if the clutter gets
  in the way.
- If Preview needs restarting after a WSL restart, `docker compose -f
  docker-compose.preview.yml up -d` brings back the existing images without a
  rebuild.

## User testing complete

### #50 — The client keeps stale game state when its session ends

Four commits. The bug is in *"the session ended"* rather than *"the account was
deleted"*, which is why there were four paths rather than one.

**Complete.** Two tested by hand, one closed by another change in this release,
one covered by tests:

| path | outcome |
| --- | --- |
| 1. Log out with a game open | **Passed** in Preview. Board, rack and games list all cleared; nothing sat behind the auth dialog. |
| 2. Account deleted while signed in | **Cannot happen** — see below. |
| 3. Session expiry | **Passed** in Preview, forced with `update sessions set expires_at = 0`. |
| 4. A 403 that is not a 401 | **Covered by tests** — see below. |

**Path 2 is closed by #82, not untested.** #82 landed in this same release and
refuses to delete an account with a live session — which is exactly the state
path 2 needs. The two changes met in the middle: the client-side handling
remains as defence in depth for a state the server will no longer produce. The
symptom it was written for was a Register dialog prefilled over a *still-visible*
board; path 3 now produces the correct version of that picture, a prefilled Log
in dialog over a cleared one.

**Path 4 is covered where it can be.** `ec72268` moved four handlers — `get_game`,
`start_game`, `submit_action`, `post_chat_message` — from 401 to 403 for a caller
who is signed in but not a participant, and gave each a test asserting
`FORBIDDEN`. Reaching them by hand needs a signed-in account acting on a game it
is not in, which the UI deliberately does not offer, so a manual test would mean
curl with a token lifted from browser storage — proving the half already under
test. The half that actually broke was the client's, and its symptom was
unmistakable: register or log in, and the app drops straight back to the login
modal. A day of repeated sign-ins did not reproduce it.

**Forcing an expiry**, for whoever needs it next — `dbpre` is `-readonly` by
design, so this is the same throwaway container without that flag:

```bash
docker run --rm -v tile-lite-elite-preview-data:/data tle-sqlite \
  sqlite3 /data/tile-lite-elite.sqlite3 \
  "update sessions set expires_at = 0 where player_id =
     (select id from players where display_name = 'Steve2');"
```

Issue #140 proposes `users logout` so this stops needing a raw write.

**Two observations, neither a defect.** The signed-out board shows a bag count
of 100 — the full-bag default rather than residue from the game just left; a
*partial* count would have been a path 1 failure. And after path 3 the login fields come
back prefilled, while after path 1 they are empty — which looks inconsistent
and is worth explaining rather than filing.

The password field is filled too, and the app never stores passwords, so the
filling is the **browser's** password manager. `auth_panel.rs` clears the
signals explicitly on log out — password always, display name unless *Remember
me* is ticked — which overwrites what the browser put there. Session expiry
never runs that code and the client never reloads, so the autofill simply
stays. The checkboxes do govern what the *app* remembers; they cannot govern
the browser. Cosmetic difference between two session-end paths, not retained
session state: the identity is gone and the board is clear in both.

### #82 — Do not delete an account that is currently signed in

`1be1f3b`. `users delete` is refused for a player with a live session.

**Complete.** Tested in Preview against `Steve44`, and the value is in the pair
— a refusal followed by a success, so the gate is shown to be reading session
state rather than refusing for some unrelated reason:

```text
$ sapre users delete Steve44
error: 400 Bad Request: That account is signed in somewhere. Deleting it now
would take an account that is in use, and one that is about to create the very
games this command refuses to orphan. Sessions end on their own: 48 hours after
they were last used, and 10 days at the outside.

$ sapre users delete Steve44
Deleted user 342c0ad3-29f5-4633-ae38-8ffaf11284a6.
```

The refusal names the reason and tells the operator what to do about it, rather
than reporting a constraint and stopping.

**Regression cover**: `cannot_delete_an_account_that_is_signed_in`
(`tests_account_lifecycle.rs`) drives the same pair through the router — 400
while signed in, then a successful delete once the sessions are invalidated —
and asserts the message says *signed in*, because a bare status check would pass
against a refusal that told the operator nothing, and there are two refusals
here whose remedies differ.

What the manual run added is what the test cannot reach: that `sapre` reaches
the admin CLI inside Preview's container, and that the wording reads sensibly to
a person.

### #86 — The unread-message indicator: where it appears, and when it clears

**Reworked during testing and complete** — `0cc012e`, api 2.12 → 2.13.

The owner's testing moved the requirement rather than just checking it, which
is what user testing is for. What shipped is not what was built:

- **each message ages on its own** against a shared visible-time clock. The
  clock used to restart on every arrival, so a brisk exchange kept everything
  unread while somebody was plainly reading it
- **one rule for unread**, read by both indicators instead of each deriving its
  own — the newest message somebody else sent, later than the watermark
- **the open game answers from live messages**, not the 10-second games-list
  poll, so a message cannot appear before its icon
- **the indicator covers every game**, because the games you are not looking at
  are the ones worth alerting about
- **gold means this game, blue means another** — the same pair on the rack and
  on the rows, so the icon says which row to look for. Clay was tried and
  rejected as too close to gold; both are warm
- **both icons take you to the messages**, switching game when that is where
  they are
- **your own messages never mark anything**, which needed
  `last_message_received_at` on the wire for the games list — caller-relative,
  like `relationship` already was
- **fades are per message** and resume rather than restart, with no colour snap
  when a message is marked read
- **the banner above the messages is gone**, so nothing jumps

Two defects were found and fixed during the round: reading your own newest
message pushed the watermark past the last one received and re-lit the row
(`!=` where `>` was meant), and making the indicator mean "any game" while the
open game's row still read it lit that row whenever anything anywhere was
unread — invisible with one game, obvious with two.

**Still not reproduced: a genuinely hidden tab.** Playwright will not background
a page, headless or headed. If something appears that the rebuild-on-visibility
explanation does not cover, that is the gap.

### #90 — Record what the database holds, daily

`3f4515a`. A row per day in `database_size_history`, written by a lazy sweep
off `list_games`, with `recorded_on` as the primary key so "once a day" is
enforced by the schema.

**How to see it.** `sapre size` — a new alias, alongside `sadev`, written into
`~/.bashrc` by `scripts/setup-dev-environment.sh`. Preview's server is in a
container and `/admin/*` only accepts loopback, so the CLI has to run *inside*
it; `scripts/admin.sh` targets the host's `127.0.0.1` and gets a 403.

Preview already has two days:

```text
DAY         PLAYERS  SESSIONS  GAMES  INVITES  CHAT  IN MEMORY  DB BYTES
2026-08-13  16       3         13     11       28    13         544768
2026-08-12  16       10        16     16       24    16         544768
```

`--json` gives the unabridged records.

**What to check:** that the numbers match what you believe is there, and that
today's row updates as you test. **A missing day means the server saw no
requests that day, not that it broke** — the sweep is lazy.

**Complete.** The one question the testing raised was what `IN MEMORY` counts.
It is the number of games held in the server's memory — which today is every
game that exists: all games are loaded at `AppState::new` and leave only when
deleted. So the column currently tracks the table rather than any working set,
and it will read the same as `GAMES` until that changes. Whether it *should*
change is #29, not this issue.
